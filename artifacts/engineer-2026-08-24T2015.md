## IS_INSECURE_MOCK derivation decision

The derivation rule (Doc 03 §10.13.4) is implemented as:

- `StubPhoneVerifier.IS_INSECURE_MOCK()` returns `true` — stubs lie about verifying.
- `StubIdDocumentChecker.IS_INSECURE_MOCK()` returns `true` — stubs lie about checking.
- `ConventionalEligibilityVerifier.IS_INSECURE_MOCK()` returns `this._phoneVerifier.IS_INSECURE_MOCK() || this._idDocumentChecker.IS_INSECURE_MOCK()` — delegation rule: ANY insecure dependency makes the composed verifier insecure.
- `ConventionalBallotService.IS_INSECURE_MOCK()` returns `this._eligibilityVerifier.IS_INSECURE_MOCK()` — delegation chain extends to the ballot service.

When real vendor integrations replace the stubs, both stub IS_INSECURE_MOCK() methods return `false`, the composed verifier returns `false`, and the CI promotion gate permits the deployment past devnet — with no interface change required. The production v1 conventional backing IS NOT A MOCK (it performs honest conventional checking); it returns `false` per §10.13.4.

## Underspecification calls flagged for approver review

**FLAG A — ver state subtitle vs v1 reality:**
The DES-094 approved subtitle for the `ver` state is "Your vote counts. Your identity is not stored." In v1, the conventional database DOES store the account↔party membership association (the subpoena-test fails; FR-128 is deferred to v2). The copy is approved verbatim per the task. The tension is recorded here: the `ver` state subtitle is a v2-accurate statement; in v1 it is aspirational rather than accurate. The DES-098 honesty notice (FR-131) is the disclosure mechanism; it is not this component's responsibility to modify the approved copy. FLAGGED for the approver's awareness — no code change made.

**FLAG B — COUNTING_ACTION scope as direct enum value vs scope-built-from-enum:**
The spec says "make verifyEligibility's scope parameter accept ONLY a counting-action scope built from these." This was interpreted as: the scope IS the COUNTING_ACTION string value directly (STRENGTH_CONTRIBUTION, BINDING_VOTE, CANDIDACY). An alternative reading would be a more complex scope (e.g., keccak256 of COUNTING_ACTION + some election/party ID). I chose the direct-enum approach for the v1 stub because: (a) v1 has no on-chain scope derivation; (b) the seam's purpose is to distinguish COUNTING from JOIN/LEAVE/account-creation, not to derive cryptographic scopes (that is the v2 ZK path). If the architect intends a more complex scope derivation for v1, the COUNTING_ACTION enum values are the right building blocks — the check in verifyEligibility would need to be a prefix check or a builder function.

**FLAG C — credentialStore seam design:**
The ConventionalEligibilityVerifier receives a `credentialStore` as a constructor dependency (Map<memberId, IdDocumentResult>). In production, this would be a database query interface. The stub uses an in-memory Map. The interface for the credentialStore seam was not formally specified in DES-095/DES-097; it was inferred from the stated requirement that verifyEligibility checks `id_verified_flag`. The current design uses a Map directly; if a formal ICredentialStore interface is needed, it should be added in a subsequent sprint.

**FLAG D — computeTally publication path:**
The audit-contract publication (on-chain write of the tally result hash) is NOT wired. The `publicationPath` field in TallyResult is set to `'PENDING-audit-contract-wiring'`. This is an intentional integration point left for a later sprint (the v1 audit-record contract subset). FLAGGED so the approver and tester know this field is a placeholder.

**FLAG E — typeface bundle deferral (DES-082/DES-093 note):**
The Fraunces and Inter self-hosting vs 15 MB install floor verification is deferred. No font files are bundled. tokens.css carries fallback stacks only. The Google Fonts CDN is blocked by the strict CSP in the PWA shell (ADR-012); self-hosting is the default requirement. This deferral is marked in tokens.css and flagged here for the next build sprint.

**FLAG F — SIM-swap recovery design (ADR-025 §(c-iv)):**
ADR-025 §(c-iv) notes that the FR-058/FR-071 recovery designs' interaction with phone-number-based account recovery requires engineering decisions that "are NOT made in this ADR" and that "a DES owed before the enrolment sprint." No recovery path was built in this session (scaffold only). Flagged for the enrolment sprint.
