## The two status calls I own — and the reasoning

### FR-130 → **CLOSES (COMPLETE)**

DES-102 (Doc 03 §10.13.11) supplied the missing link and bound SCR-09/SCR-11, so rule 1 is
satisfied; rules 2–3 already were. **Rule 4 holds** because each clause of the stated guarantee has
its own passing test, not a proxy for one:

- **cap at 100 while unverified** — 100th join succeeds, 101st refused `PROVISIONAL_CAP_REACHED`
  unconditionally, and a leave frees **exactly one** slot, so the cap tracks ACTIVE membership
  rather than cumulative joins (UT-0825, UT-0802..0805, UT-0862);
- **lift by code only on verified registration** — automatic, no admin call in the path
  (UT-0809..0811, TC-3515);
- **no operator or manual early-lift path** — first-class capability-absence: no admin API, config
  flag, env var or code path raises the cap (UT-0806, TC-3514).

**Why the v1 residual does not block it.** DES-102 rule 8 is honest that v1 gives audit-record
**tamper-evidence**, not tamper-prevention, and rule 7's `Party.join()` guard is unbuilt — I checked
`packages/contracts/src/core/Party.sol` and `join()` does `memberCount += 1` with no cap check,
precisely where DES-102 says the guard belongs. But that is an **enforcement-tier upgrade, not an
unmet clause of FR-130**. In v1 there is no on-chain membership at all (ADR-024 §(b)), so the
application/Postgres write boundary is the only enforcement point that exists, and the invariant is
tested there. Critically, **FR-011, FR-020 and FR-022 already stand COMPLETE on exactly this
posture** — an operator with direct DB access can bypass any v1 application boundary. Holding FR-130
alone to a stricter bar would be special-pleading, not rigour.

I recorded the residual **inside the row** and flagged that **the row MUST be revisited when
on-chain membership goes live**, at which point the uncapped `Party.join()` becomes a live bypass
rather than a dormant one.

*Sanity check against the incentive:* closing FR-130 moves open Must rows 126 → 125. That is
cosmetically nothing against a zero-gap rule, so there was no number-driven pull either way. The
call is on merit.

### FR-077 → **DOES NOT CLOSE — reclassified G-TRACE → G-NOMECH**

DES-101 closes the *chain* gap (rules 1–3 satisfied; publication half passes at protocol + sdk +
web). **Rule 4 fails, on a finding the architect's §15 assessment missed.**

FR-077's stated guarantee is refusal at publication **AND** at "**every subsequent amendment**".
Only publication is verified, and **nothing implements the amendment half at either tier**:

- **Application:** there is no charter-amendment path at all — `validateDraft` is called only at
  `createDraft` (party-creation.js:547) and `publishDraft` (:663).
- **On-chain:** `Party.amendCharter` (`packages/contracts/src/core/Party.sol` ~line 350) sets
  `charter.charterHash` and `charterCID` after checking only `msg.sender == governor` and
  `immutableClause[clauseId]`. It stores a hash and a CID — **it never sees the charter text** and
  performs no clause verification. A constitutional-tier amendment naming any *other* clauseId can
  install a charter with the non-violence clause stripped, and nothing refuses it. Grep for
  `nonviolence|non_violence` across `packages/contracts/src` returns **nothing**.

Rule 4 is explicit that a **fragment** of a guarantee does not close a row. The architect assessed
the gate as "a verbatim-match refusal" — true of publication, and the half that was in front of
them. Amendment-time clause verification is **undesigned**, and I routed it to the architect.
