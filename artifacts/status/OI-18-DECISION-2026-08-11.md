## 1. What OI-18 was

OI-18 was the entrenched-charter scope question that surfaced when Doc 02 reached v2.1.0. The
approver's existing entrenched list contained six platform rules — one human one vote; no
transferable power; no privileged role over outcomes; the unconditional right to fork; no
behavioural surveillance; anonymity by default with disclosure only by voluntary role-taking —
codified in FR-118, which requires code to reject any amendment proposal targeting these rules at
submission. A separate class of previously-absolute guarantees — CON-001 (party-only boundary,
never state elections), BR-011/NFR-003 (receipt-freeness and coercion resistance), CON-002,
CON-008, NFR-010 (data minimisation), CON-012 (no bespoke unaudited cryptography), and CON-013
(non-violence clause) — were stated as absolute throughout the document but lay outside the
entrenched charter, meaning FR-119 (highest-tier citizen vote with timelock) would make them
amendable. Three options were presented: (a) extend the entrenched charter to include all named
absolutes; (b) accept that they become amendable at the highest tier, recording that as a
deliberate weakening; (c) a two-tier core — the six charter rules remain fork-only, the named
absolutes become amendable only by a stricter super-process defined in Design. The decision was
required from the approver before the architect could fix the amendment boundary in Doc 03; a
⚠ banner was placed after FR-118 in §4.39 of Doc 02 v2.1.0 to hold the space open.

---

## 2. The decision — quoted verbatim

> "OI-18: OPTION (c) — TWO-TIER CORE, with one change.
>
> Tier 1, entrenched charter, unamendable by any vote, changeable only by fork: the existing six
> rules, PLUS CON-001 (parties only, never state elections). CON-001 is promoted because it is a
> scope boundary rather than an implementation commitment — a platform that could vote itself into
> running state elections becomes a categorically different and more dangerous system.
>
> Tier 2, named absolutes, amendable only via a super-process the architect specifies in Doc 03:
> receipt-freeness and coercion resistance (BR-011, NFR-003); data minimisation (CON-002, CON-008,
> NFR-010); no bespoke unaudited cryptography (CON-012); the non-violence clause (CON-013).
>
> The super-process MUST require, at minimum: a supermajority materially above the ordinary
> structural tier; a timelock long enough that the fork right is genuinely exercisable before the
> change takes effect; two consecutive affirmative votes separated by that window so a transient
> majority cannot carry it; the growth-surge defence active throughout; and an independent audit
> of the proposed change published before the second vote. The architect sets the specific numbers
> and records them with rationale.
>
> Rationale to preserve in the record: receipt-freeness is the case that makes the tiering
> necessary. It must survive an ordinary majority — a majority voting away receipt-freeness is a
> majority voting to make everyone coercible, including the minority most at risk. But it is still
> an implementation commitment: if a better coercion-resistance technique emerges there must be a
> legitimate path to adopt it. Tier 1 defines what the system is; Tier 2 protects people from a
> majority while remaining evolvable.
>
> Tier 3 — everything else — remains amendable by ordinary citizen vote at its normal tier."

## 3. Disposition summary

| Tier | Members | Amendment path |
|------|---------|----------------|
| **Tier 1 — Entrenched charter (fork-only)** | The six existing charter rules (one human one vote; no transferable power; no privileged role over outcomes; the unconditional right to fork; no behavioural surveillance; anonymity by default with disclosure only by voluntary role-taking) **plus CON-001** (parties only, never state elections — promoted because it is a scope boundary, not an implementation commitment) | Unamendable by any vote at any tier. Changeable only by fork. Code rejects amendment proposals at submission (FR-118). |
| **Tier 2 — Named absolutes (super-process only)** | BR-011 / NFR-003 (receipt-freeness and coercion resistance); CON-002 / CON-008 / NFR-010 (data minimisation; no personal data on the governance record); CON-012 (no bespoke unaudited cryptography); CON-013 (non-violence clause) | Super-process only — five minimum properties the architect specifies in Doc 03: **(1)** supermajority materially above the ordinary structural tier; **(2)** timelock long enough that the fork right is genuinely exercisable before the change takes effect; **(3)** two consecutive affirmative votes separated by that window (no transient majority can carry it); **(4)** growth-surge defence active throughout; **(5)** independent audit of the proposed change published before the second vote. The architect sets the specific numbers with rationale. |
| **Tier 3 — Everything else (ordinary tier)** | All remaining protocol rules and governance parameters not enumerated in Tier 1 or Tier 2 | Ordinary citizen vote at its normal tier per FR-119 (highest-tier quorum, supermajority, timelock as set at OI-17 closure; enacted by code with no ratification step). |

## 4. What this decision unlocks

The design phase may proceed. The architect produces **Doc 03 v2** covering:

- **FR-118 / FR-119 amendment boundary.** Tier 1 (fork-only) and Tier 2 (super-process) are now
  defined at requirements level. Doc 03 must specify the Tier-2 super-process with concrete
  numbers and rationale for all five minimum properties and mint corresponding DES elements and
  an ADR.
- **SC-13 / SC-14 trust-anchor governance design.** FR-112/FR-113 (trust-anchor lifecycle events
  as member-vote actions executed by code, ruling 4) are resolved in principle; the Doc 03 design
  change is owed and remains open against the architect.
- **OI-17 governance constants.** Quorums, timelocks, supermajority thresholds, and cooldown values
  for steward elections and conduct votes (FR-114..FR-119) are to be set by the architect (Tomás
  Ferreira) in Doc 03 with rationale.
- **DES elements for FR-114..FR-120** — the full steward-organisation design — including FR-117's
  capability-absence obligation (a complete steward vacancy must cause zero citizen-facing
  degradation: enrolment, party creation, voting, proposal submission, and forking all proceed
  unchanged).
